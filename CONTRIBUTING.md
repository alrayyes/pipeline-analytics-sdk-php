# Contributing

## Requirements

- PHP 8.2 or later (this machine's own PHP works fine -- `rules/php.md`'s
  Docker fallback is for a machine with none, which isn't the normal case
  here).
- [Composer](https://getcomposer.org/) 2.x.
- [Docker](https://www.docker.com/), for regenerating `generated/` only --
  `openapi-generator` needs a JVM, and the pinned Docker image is simpler
  and more reproducible than requiring a matching local Java install.
- [lefthook](https://github.com/evilmartians/lefthook) and
  [bun](https://bun.sh) (for commitlint). `bun install` then
  `lefthook install` once, after cloning.

## Generator choice

Unlike the Go, TypeScript and Python SDKs, there's no clearly-superior
lightweight PHP-specific generator the way `oapi-codegen`/
`openapi-typescript`+`openapi-fetch`/`openapi-python-client` are for those
languages. This repo uses [openapi-generator](https://openapi-generator.tech/)
itself, target `php` (not `php-nextgen`), for two concrete, checked reasons:

- `php`'s own metadata reports `generator stability: STABLE`;
  `php-nextgen`'s reports `BETA`
  ([php.md](https://github.com/OpenAPITools/openapi-generator/blob/master/docs/generators/php.md),
  [php-nextgen.md](https://github.com/OpenAPITools/openapi-generator/blob/master/docs/generators/php-nextgen.md)).
- `php` has a `library` config option (`guzzle` or `psr-18`) that picks the
  HTTP client the generated code is built around; `php-nextgen` has no such
  option at all (confirmed via `openapi-generator-cli config-help -g
  php-nextgen` against the pinned v7.25.0 image), so there's no way to ask
  it for a Guzzle-based client explicitly.

This is a real tradeoff, named rather than defaulted to
(`rules/sdk-generation.md`'s "Generator choice"): openapi-generator's PHP
templates are generic, not hand-tuned for PHP idiom the way a
PHP-specific generator would be, but it's the best available option today.
`library: guzzle` was chosen over `library: psr-18` because Guzzle's own
`Client` already implements PSR-18's `ClientInterface`, so the generated
code gets a concrete, retry-middleware-friendly HTTP client without asking
every consumer to supply their own PSR-18 implementation.

## Generated vs hand-written

`generated/` is the entire output of `scripts/generate.sh` -- namespace
`PipelineAnalytics\Generated`, one class per spec schema and per tag's
operations. Every file in it carries a "Do not edit the class manually."
notice in its docblock (openapi-generator's own convention, the PHP
equivalent of the `// Code generated by <tool>; DO NOT EDIT.` header other
languages get). Never hand-edit anything under `generated/` -- Pint,
Rector and PHPStan are all scoped away from it, and CI's
`generated-code-is-fresh` job re-runs the generator and diffs the result
against what's committed, catching both a stale pin and a hand-edit that
crept in.

Everything else -- `src/Client.php` (the constructor, retry/cookie wiring),
`src/Retry/`, `src/Exception/`, `src/Pagination/` -- is hand-written on top
of the generated package, never inside it.

### Regenerating the client

```sh
./hack/fetch-spec.sh      # re-fetches openapi/openapi.yaml at the pinned commit
./scripts/generate.sh     # regenerates generated/ from that spec
```

The spec itself is pinned to a commit of
[alrayyes/pipeline-analytics](https://github.com/alrayyes/pipeline-analytics)
recorded in `openapi/SPEC_COMMIT`; `.github/workflows/regenerate.yml` bumps
that pin weekly and opens a pull request when pipeline-analytics' spec has
moved. Diff `openapi/openapi.yaml` (not the generated PHP) to decide
whether a change needs a major, minor or patch bump -- see
`rules/sdk-generation.md`'s "Versioning tracks the contract, not the
commits".

## Building and testing

```sh
composer install
composer test              # PHPUnit
composer phpstan           # level 9, generated/ excluded
vendor/bin/pint --test     # formatting check
composer rector:lint       # mechanical-upgrade check, dry run
composer normalize --dry-run
composer audit
```

`lefthook run pre-push` runs the same set, so that's the one command to run
before opening a pull request.

Tests only cover the hand-written parts -- retry backoff, cookie injection,
error decoding, pagination -- against a Guzzle `MockHandler`, never the
generated request/response mapping itself (`rules/sdk-generation.md`'s
"Testing against the spec, not a hand-written stub": testing the generated
type mapping again is testing the generator, not this SDK).

## Commits and releases

Commit messages follow [Conventional
Commits](https://www.conventionalcommits.org/), linted by commitlint on
`commit-msg`. Merging to `main` is what
[release-please](https://github.com/googleapis/release-please) reads to
keep an open release pull request with the next version and changelog;
merging that pull request tags the release. `release-type: php` in
`release-please-config.json` -- release-please's own PHP strategy updates
a `version` field in `composer.json` only if one already exists, and this
repo deliberately doesn't declare one (Composer/Packagist resolve versions
from Git tags, not the manifest), so that update is a no-op and the tag is
what actually matters.

## Branching

Every change lands through a pull request; nothing is pushed straight to
`main`.

## Release tagging note

`v0.1.0` is the real baseline release-please computes from -- it was
retagged once after an early mistake pointed the tag at an orphaned
squash-merge source commit instead of the actual `main` HEAD, which made
release-please treat the repo as having no prior release at all and
propose `1.0.0` (github.com/alrayyes/pipeline-analytics-sdk-php#3, #5, #7,
#9, #11). If a future release ever proposes an unexpectedly large jump,
check `git tag -l -n1` against `git log main` before assuming
`release-please-config.json` is wrong again.
